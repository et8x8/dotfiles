# GitHub PRの公開

## 公開前の確認

次の確認を必須とする。

1. リポジトリの指示と公開に関する規約を読み、従う。
2. Git の状態、現在のブランチと HEAD、リモート、現在の作業に関係する既存の pull request を確認する。
3. 既存の pull request がある場合はその base を使用する。ない場合はリモートのデフォルトブランチを意図した base とし、明確に判断できない場合は停止してユーザーに確認する。
4. 秘密情報を読み取らずに、保留中の差分全体を確認する。
5. 差分にリポジトリで禁止されたファイルが含まれている場合は停止して報告する。そのファイルを確認、stage、変更、公開してはならない。
6. `.env.keys` を読み取らず、環境変数の値を検査、表示、確認、公開してはならない。

## コミットメッセージと PR 本文

PR は Squash and merge で target branch に統合され、PR 本文は結果のコミットメッセージの一部になる。後から差分とメッセージを読む人や AI エージェントが、何をなぜ変更したかを理解できるように書く。この skill を実行するセッションが実装したセッションと異なっても背景を取りこぼさないよう、コミットメッセージにも PR 本文と同じ構成で書く。

### 情報源

- 会話、base からのブランチの全コミットメッセージ、既存の PR 本文、差分を情報源とする。
- PR 本文は、PR の全コミットをまとめて最新の差分に合わせた内容にする。後のコミットで取り消された変更や古くなった記述は含めない。
- 既存の PR 本文の内容は、最新の差分と矛盾せず、次の見出しに当てはまるものを引き継ぐ。
- 背景が情報源に見つからない場合や、差分にコマンドで生成・変更されたとみられるファイルがあるのにコマンドの記録が無い場合は、推測で書かずに、コミットや PR の作成・更新の前にユーザーへ質問する。

### 見出し

ユーザーから言語の指定がある場合はその言語で記述する。指定がない場合は、他のコミットと同じ言語で記述する。ただし見出しは、使用する言語にかかわらず次の英語の見出しをこの順に使う。書く内容が無い見出しは省略する。

- `## Changes`: 変更内容の箇条書き。ライブラリやフレームワークの開発者向け CHANGELOG にそのまま載せられる粒度で書く。ファイルの配置や一覧への追記など、差分を見れば分かる項目は書かない。
- `## Background`: 変更した理由。ユーザーが示した背景や、変更に関わる制約や今後の対応など、差分に残らない背景を書く。ユーザーに質問して差分以上の背景が無いと回答された場合は省略する。
- `## Commands`: コミットされたファイルを生成・変更・削除したコマンド（init や generate、パッケージの追加・削除、フォーマッタ、codemod など）を、パラメータとともに実行順にコードブロックで書く。対話的なプロンプトで選んだ値は、コードブロックの後に箇条書きで補う。コマンドの出力や、検証・調査のコマンドは書かない。

### 書かない内容

- 変更と無関係な情報。
- 検証の内容、結果、未検証の事項。
- ファイルの状態や生成物の中身など、差分やログを読めば分かる細部。`## Changes` の要約は除く。
- この skill を実行したセッションでしか理解できない内容。記述が必要な場合は、そのセッションを知らない読者が理解できる背景を添える。
- コミットを理解するために直接必要でない限り、pull request の作業状態、レビューの進行、draft/ready の理由、レビュアーへの指示、その他の作業手順。
- 使用した AI エージェント、モデル、ツールの宣伝、署名、生成元の表記（`Generated with ...` など）、謝辞、リンク。エージェントやツールの既定の出力形式に含まれていても削除する。ただし、そのエージェントやツール自体が変更対象であり、変更の説明に必要な言及は含めてよい。

## ブランチとコミットの準備

- HEAD が detached であるか base ブランチを checkout している場合は、変更内容から簡潔なスラッグを作成し、衝突しない feature branch を作成する。
- それ以外の場合は、公開が安全でない、または判断が曖昧でない限り、現在の feature branch を維持する。
- 対象範囲内で許可された未コミットの変更だけを stage する。
- 既存の履歴を維持し、stage した変更に対して新しいコミットを1つだけ作成する。コミットする差分がない場合はコミットを省略する。
- コミットメッセージは、件名1行（PR タイトルと同じ基準）、空行、本文とする。本文は「コミットメッセージと PR 本文」節に従い、そのコミットの変更について書く。
- 通常の commit hook を実行する。hook を無効化したり `--no-verify` を使用したりしてはならない。

## 安全な push

- feature branch を適切な remote へ push する。
- 通常の force push は絶対に使用しない。
- base ブランチが進んだことだけが原因で push が拒否された場合は、fetch して更新後の base へ rebase する。
- その rebase で競合した場合は、競合を解決せずに停止する。
- 成功した base 更新の rebase によって、feature branch ですでに公開済みのコミットが書き換えられた場合に限り、`--force-with-lease` を使用する。
- feature branch の分岐、予期しないリモート履歴、曖昧な upstream、または base の進行だけでは説明できない拒否が発生した場合は、停止して続行前にユーザーへ確認する。

## Pull request の作成または更新

- Pull request がない場合は、Draft pull request を作成する。
- ある場合は、現在の draft または ready の状態を維持し、タイトルと本文を更新する。
- PR を作成または更新する前に、末尾の自動追加文を含む本文全体を将来の squash commit message として読み直し、「コミットメッセージと PR 本文」節に反する文や、merge 後の `git log` では意味をなさない、または誤解を招く文を削除する。
- PR のタイトルは、`git log --oneline -20` が最近の変更を最も確実に簡潔に記録できるように書く。
- 確認済みの base branch を対象にする。
- pull request を merge してはならない。
