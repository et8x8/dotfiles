# grill-spec

要件定義と基本設計を、ユーザーへの質問で固めて文書に残す。それらに基づく実装も行う。

AIが出す質問は、人間が一度に答えるには多い。このスキルの規則は、ユーザーが「どれに今答え、どれを後に回し、どれを委ねるか」を素早く選別できるようにするためにある。

## 開始時の手順

1. `grilling` スキルと `domain-modeling` スキルを呼び出し、質問の進め方はこれらに従う。どちらかが導入されていなければ、その旨を伝えて終了する。
2. 既存の `REQUIREMENTS.md`、`SPECIFICATION.md`、`DESIGN.md`、`TASK.md`、`docs/design/`、`CONTEXT.md`、その他の関連資料を読む。文書が既にあれば続きから再開し、未決事項は質問として出し直す。既存の文書の識別子の有無と付け方も確かめる。
3. 取り扱う工程を「要件定義」「基本設計」「実装」の中から確定する(複数でもよい)。ユーザーが名前を挙げた工程だけを取り扱い(「まず要件定義を」なら要件定義のみ)、その解釈を最初のメッセージで伝える。読み取れなければ、他の質問より先にこれだけを聞く。この質問は保留や不問にできない。

## 工程

| 工程 | 行うこと | 成果物 |
| --- | --- | --- |
| 要件定義 | WHAT(何を作るか)、WHY(なぜ作るか)を定める | `REQUIREMENTS.md` |
| 基本設計 | HOW(どのように作るか)、WHERE(どこに作るか)を定める。画面設計を含む | `SPECIFICATION.md`、`docs/design/` |
| 実装 | 要件定義と基本設計に従って実装する。画面は `DESIGN.md` に従う | コード、`DESIGN.md`、`TASK.md` |

- 工程は表の順に進める。複数の工程を取り扱う場合も、1つの工程が完了したら、完了を伝えて、次の工程に進んでよいかを聞く。前の工程の成果物が無い、または優先度「高」の未決事項が残っていれば、その事実も同じ質問に添える。前の工程の内容を推測して進めない。
- 次の工程に進むかの質問は、保留や不問にできない。進まないと答えられたら、そこで終える。
- 要件定義と基本設計は、その工程の質問がすべて回答済み、保留、不問のいずれかになった時点で完了とする。完了時に、成果物のパス、未決事項の数(優先度ごと)、不問とした事項の数を伝える。実装の完了の基準は「実装」に定める。
- 画面を持たない対象(CLIやライブラリなど)では、画面設計と画面の実装を行わない。

### 現在の工程で決めることだけを聞く

質問を出す前に、1問ずつ「その答えが無いと、現在の工程の成果物が書けないか」を確かめる。書けるなら、その質問は後の工程のものなので聞かない。前提が固まる前の質問は答えが後で覆りやすく、ユーザーが今答えるべき質問も埋もれてしまう。

| 行っている工程 | 聞かないこと |
| --- | --- |
| 要件定義 | 基本設計以降で決めること(採用する技術、システムの構成、配置、開発・テスト環境、画面の構成など) |
| 基本設計 | 詳細設計以降で決めること(関数やクラスの分割、テーブルの列の型や索引、APIの項目ごとの定義、アルゴリズム、メッセージの文言、画面要素の寸法や色など) |
| 実装 | 選ばれたタスクの実装に必要ないこと |

- 後の工程で決める事柄は、未決事項にも記録せず、残り質問数にも数えない(未決事項は、現在の工程で聞いて保留された質問のためのものである)。
- ユーザーが後の工程の事柄も決めたいと指示した場合は、指示された範囲に限って聞く。
- 詳細設計以降の粒度の事柄でも、ユーザーが明示的に要求したもの(例: 特定バージョンのソフトウェアに依存したシステムの改修)は、制約として要件定義に記録する。基本設計の途中で出てきた場合も `REQUIREMENTS.md` に追記し、既存の要件と矛盾しないかを確認する。

## 質問の出し方

今聞ける質問を1ラウンドでまとめて出し、推奨回答を添える `grilling` の方式に、次の規則を加える。

- 出力の冒頭、質問の直前に残り質問数を出す。
- ラウンド内の質問は優先度の高い順に並べる。
- 各質問に工程、優先度、保留した場合の影響を付ける。
- 既存資料に関する質問には、ユーザーが該当箇所を探さなくて済むよう、資料の場所をファイルパスと行番号(または節番号や節名)で示す。指す項目に識別子があれば添える。
- 選択肢がある質問では、選択肢を文中に並べず、`(a)` `(b)` のような記号を付けて1つずつ箇条書きにする。推奨回答は記号で指す。
- 推奨する根拠が無い質問(予算の上限など、ユーザーしか知りえない事柄)では、推奨回答の行を省く。「推奨できない」とも書かない。根拠の無い推奨も、同意されれば仕様になってしまう。
- 空行は質問と質問の間にだけ入れ、1つの質問の中には入れない。どこまでが1つの質問かを一目で分かるようにするためである。
- 最初のラウンドの末尾にだけ、各質問へは回答、保留、不問のいずれかで答えられることを1行で添える。
- 保留や不問にできない質問(工程の確定、次の工程に進むか、実装するタスクの選択)には、残り質問数、工程と優先度、保留時の影響、回答の種類の案内を付けない。

出力の形(識別子の内容の行は質問に識別子が現れたときだけ、「資料」の行は既存資料に関する質問のときだけ、選択肢は選択肢がある質問のときだけ出す):

```
残り質問数(概算): 高 2 / 中 3 / 低 1 / 計 6(保留 1)

❓ **Q3** [要件定義 / 高] - **対象ユーザーの範囲**:
SC-0002 の「利用者」に、未ログインのユーザーを含めますか?
`SC-0002`: 利用者は、自分の文書をアップロードしてチェックを実行できる。
資料: REQUIREMENTS.md:42(SC-0002)
保留時の影響: <手戻りが及ぶ範囲>
- (a) 含める
- (b) 含めない
➡️ (a) <推奨する理由>

❓ **Q4** [要件定義 / 中] - **<題名>**:
<質問本文>
```

「❓」と「➡️」は `grilling` の形式に由来する質問の目印であり、絵文字を避ける指示がある環境でもそのまま使う。

### 質問の目的

質問は、仕様を明確にするため、または仕様の疑問点を解決するために出す。答えによって文書に書く内容が変わらない質問は出さない。

- 既に合意が取れたことを再確認しない。回答をそのまま文書に書けるなら、書いて次へ進む。
- 成果物(文書や画面設計の資料)や既存のコードに問題が無いかを確認するだけの質問をしない。書き足した内容とファイルパスは通常の出力で伝える。実装の工程でデザインの合意を取るための仮画面の確認だけは例外とする(「画面の実装」)。
- 回答が複数の解釈を許す場合や、既にある合意と食い違う場合に聞き直すのは、疑問点の解決なので再確認には当たらない。

### 質問の手段

エージェントに質問用の機能があれば、質問はそれを使って出す。Claude Code では `AskUserQuestion`、Codex では `request_user_input_async`、それ以外のエージェントでは同等の機能がこれに当たる。ラウンドの質問に限らず、工程の確定など、このスキルでユーザーに尋ねることすべてに当てはめる。

- 残り質問数と、最初のラウンドの回答の種類の案内は、質問用の機能を呼び出す直前に通常の出力として出す。
- 質問文には、「出力の形」の質問1つ分のうち、選択肢と推奨回答を除いた行をそのまま入れる。ユーザーは質問用の画面だけを見て答えるので、識別子の内容、資料の場所、保留時の影響を通常の出力の側に分けない。
- 選択肢は質問用の機能の選択肢として渡す。推奨回答は、その機能に推奨の示し方があればそれに従い、無ければ選択肢の説明に書く。どちらの場合も推奨する理由を添える。
- 任意入力欄を必ず設ける。選択肢に無い答え、質問の一部だけへの答え、保留、不問を、ユーザーが選択肢に縛られずに返せるようにするためである。機能が自動で付ける場合(`AskUserQuestion` の「Other」など)はそれでよく、付けない場合は自分で加える。
- 選択肢の無い質問で、機能が選択肢を必須とする場合は、「保留」と「不問」を選択肢にし、回答は任意入力欄に書いてもらう。選択肢のある質問でも、選択肢の数の上限に余裕があれば「保留」と「不問」を加える。保留や不問にできない質問には加えない。
- 1回に出せる質問の数に上限があれば、優先度の高い順に分けて、続けて呼び出す。
- 回答を受け取ったら、確定した分を文書に書き足し、同じターンのまま次のラウンドを出す。工程の質問がすべて回答済み、保留、不問のいずれかになるまで、ターンを終えない。途中で終えると、ユーザーが再開を指示するまで質問が止まってしまう。
- ユーザーが回答せずに質問用の画面を閉じた場合は、同じ質問を出し直さず、確定した分を文書に残したうえで、残りの質問を通常の出力として出してターンを終える。

質問用の機能が無いエージェントでは、「出力の形」のとおりに通常の出力として質問を出し、ターンを終えて回答を待つ。

### 識別子の内容

質問に識別子を書くときは、その項目の文面を同じ質問の中に添え、質問をその質問だけを読んで答えられる形にする。識別子だけでは、ユーザーは文書を開いて該当の項目を探さなければ答えられない。

- 題名、本文、選択肢、「資料」の行、推奨回答のどこに現れた識別子も対象とする。
- 本文の直後に、識別子1つにつき1行で `` `識別子`: <項目の文面> `` の形で書く。文中に言い換えとして埋め込まない(どこまでが文書の文面なのかが分からなくなる)。
- 文面は要約せず、文書からそのまま写す。要約すると、文書に無い解釈が混ざる。
- 同じラウンドや以前のラウンドの別の質問で既に内容を示した識別子でも、質問ごとに改めて添える。ユーザーは質問を1つずつ選別して答えるので、他の質問までさかのぼらせない。
- 子項目を持つ項目を指すときは、質問に関わる子項目も同じ形で添える。
- 項目の変更を提案する質問では、現在の文面に加えて、変更後の文面も示す。

### 残り質問数

現在の工程について、今回出している質問と今後発生する見込みの質問を合わせた概数を、優先度ごとの数と合計で示す。その時点の見積もりでよい。

保留された質問は含めず、括弧内に別枠で示す(無ければ括弧を省く)。不問とされた質問は回答済みとして扱う。

### 前工程との矛盾

資料やユーザーの回答から、前工程の内容(基本設計中であれば `REQUIREMENTS.md`)と矛盾する点が見つかったら、優先度によらずラウンドの先頭で聞く。矛盾の答えに左右される質問は、答えが出るまで出さない。無関係な質問は同じラウンドで出してよい。

合意されていない資料(議事録や要望メモなど)が前工程の文書と食い違う場合も同じ扱いとし、「どちらが正しいか」ではなく「前工程の内容を変更するか」を聞く。合意済みの文書は、ユーザーが変更に同意するまで正とする。

食い違っている両方の箇所を、資料の場所つきで示す。前工程の文書を直す場合は、変更するファイルパスと節を示してから修正する。

## 優先度

優先度は、その質問を保留した場合に生じる手戻りの影響範囲である。重要そうに見えるかどうかではなく、後回しにしたら何が壊れるかで判断する。

| 優先度 | 基準 |
| --- | --- |
| 高 | 手戻りが次工程以降、または文書全体に及ぶ。回答が無いと次工程に着手できないもの、後で答えが覆ると手戻りが大きいもの(スコープの確定は原則これに当たる) |
| 中 | 手戻りが現在の工程の文書の複数箇所に及ぶ |
| 低 | 手戻りが1箇所に収まる |

例外として、事業、法務、契約、進行前の合意が必須の事項は、後回しにすると前提から覆る可能性が高いので、手戻りの範囲によらず「高」とする。

実装の工程では、次の基準を使う。

| 優先度 | 基準 |
| --- | --- |
| 高 | 手戻りが他のタスク、または文書に及ぶ |
| 中 | 手戻りが選ばれたタスクの中の複数箇所に及ぶ |
| 低 | 手戻りが1箇所に収まる |

## 回答の種類

文書に書く内容は、すべてユーザーと合意が取れたものでなければならない。些細なことでも、独断で仕様の一部を補ったり決めたりしない。質問として出し、合意を得てから書く。文書は合意の記録であり、合意していない記述が1つでも混ざると、読み手はどれが合意済みなのかを区別できなくなる。

- 「決めた内容を後から報告して確認を取る」方式は認めない。通常の出力に埋もれて見落とされ、確認したことにならないからである。
- 文章を整える途中で、合意に無い細部(数値、条件、例外時の扱いなど)を書かないと文が成り立たないと気付いたら、補わずに質問として出す。
- 一般的にはこうするはずだ、という推測も合意ではない。
- 決まっていないことは、決まっていないこととして文書に残す。

ユーザーは各質問に次の3通りで答えられる。

**回答**: 内容を決める。

- 推奨回答は、ユーザーが明示的に同意するまで仕様ではない。
- 回答が質問の一部にしか触れていなければ、残りを推測で埋めず、次のラウンドで聞き直す。
- ユーザー本人が依頼文などで明示した内容は、質問への回答でなくても確認せずに書いてよい。複数の解釈ができる記述は、書く前に質問で確かめる。
- 議事録や要望メモなど、誰が合意したか分からない資料の記述は、前工程と食い違っていなくても書かず、資料の場所を示して質問で確かめる。

**保留**: 今は答えず、後で答える。

- どの優先度の質問でも保留できる。保留した場合の影響は質問に添えてあるので、「高」であっても保留でよいかを聞き直さない。
- 保留された質問と、それに依存するため出せなかった質問を、工程の文書の「未決事項」節に、優先度と手戻りの影響範囲つきで記録する。回答待ちの質問は書かない。実装の工程での記録先は「実装」の「質問すること」に従う。

**不問**: 内容を問わず、実装時に任意に決めてよいとする。

- 不問は「問わないと決めた」という決定なので、その事柄が属する章や節の該当箇所に、何が不問であるかと、実装時に任意に決めてよい旨を書く。不問だけを集めた節は作らない(どの部分の話なのかが文書の構成から読み取れなくなる)。
- 不問も合意の1つであり、ユーザーがその事柄を不問にすると答えた場合にだけ書ける。話題に出なかった、こだわりが無さそうだ、という推測で不問にしたり、内容を代わりに決めたりせず、質問として出して不問という回答を得る。
- 「任せる」のように、推奨回答の採用なのか不問なのかが読み取れない回答は、どちらであるかを聞く。
- 推奨回答は記録しない(事実上の仕様に見えてしまう)。
- 不問とされた事項が決まらないと成り立たない質問は出さず、文書にも個別には書かない。それ以外の質問は、不問とされた事項に関わるものでも通常どおり出す。
- 不問は実装者への委任であり、このスキルへの委任ではない。要件定義で不問とされた事項が基本設計で決めないと進めない場合は、基本設計の質問として改めて聞く。

## 文書

ラウンドごとに、確定した分を文書へ書き足す。途中で中断しても確定分が残り、次回はそこから再開できる。`CONTEXT.md` とADRは `domain-modeling` の方式のまま扱う。

`REQUIREMENTS.md` と `SPECIFICATION.md` は、`CONTEXT.md` と同じ場所に置く(`domain-modeling` が定める場所で、通常はリポジトリのルート)。

節構成は次のとおり固定し、該当する内容が無い節は省く。

`REQUIREMENTS.md`:

```markdown
# 要件定義

## 目的
## 用語定義
## 接頭辞
## スコープ
## スコープ外
## 要件
## 制約
## 未決事項
```

- 用語定義: プロジェクト固有の用語や業界特有の専門用語を定義する。`CONTEXT.md` には文書を読むだけの人に不要な用語も含まれるので、それとは別に書く。両方に載る用語は、定義の意味が食い違わないようにする。
- スコープ外: 取り扱わないと明確に決めたことだけを書き、話題に出なかっただけのことは書かない。「検討漏れ」と「意図して外した」を後から区別できるようにする。
- 制約: ユーザーが明示的に要求した、詳細設計の粒度の事柄を含む。

`SPECIFICATION.md`:

```markdown
# 基本設計

## 接頭辞
## 構成
## 配置
## 開発・テスト環境
## 画面設計
## 未決事項
```

- 構成: どのように作るか。
- 配置: どこに作るか。
- 開発・テスト環境: 開発中とテストで使う環境の取り決め。本番の構成と配置だけでは、依存サービスやテスト用のデプロイ先を開発者ごとに用意することになり、環境ごとに動作が食い違う。依存サービスもデプロイも無い対象を除き、次を質問で固める。
  - 依存サービス(外部API、データベース、メール送信、認証基盤など)ごとに、開発時とテスト時にどう用意するか(ローカルで起動する、モックやエミュレーターで置き換える、検証用のインスタンスや提供元のサンドボックスを使うなど)。開発時とテスト時で異なってよい。
  - テスト用のデプロイ(デプロイ先、デプロイの契機と手順、本番環境との違い)。
  - テストデータをどう用意するか。
- 画面設計: 画面遷移の図と、`docs/design/` 以下の資料への参照。`DESIGN.md` があれば、そのパスへの参照も書く。

### 用語定義の書き方

1つの用語を箇条書きの1項目とし、用語を太字にして、同じ行に定義を続ける。

```markdown
- **チェックリスト**: チェック対象ファイルをチェックするときに従う、複数のルールを順番に並べたもの。
```

「する」を付けるだけで動詞になる単一の語(「公開」「共有」など)は、用語定義に入れない。入れると用語定義が増えすぎて煩雑になり、その語を動詞として使ったときに定義した用語なのか一般の動詞なのかが紛らわしくなる。他の語と組み合わせた語(「移譲リクエスト」など)は入れてよい。

### 識別子

文書の項目には識別子を付ける。行番号や節番号は編集のたびにずれるが、識別子はずれないので、質問、もう一方の文書、文書の外(議事録やコミットなど)から同じ項目を指し続けられる。

- **項目**: 識別子を付ける対象の1件。箇条書きの1つに当たる。
- **識別子**: 接頭辞、番号、子番号をハイフンでつないだもの(`FR-0001`、`NR-0003-01`)。
- **接頭辞**: 項目の種類を表す英大文字2〜4文字。
- **番号**: ゼロ埋めした4桁の数字。
- **子番号**: ゼロ埋めした2桁の数字。子項目に付ける場合にだけ使う。

「目的」「用語定義」「接頭辞」を除く各節の項目に付ける。不問とした事項にも付ける。分類用の小見出しには付けない。

箇条書きの先頭に太字で書く。

```markdown
- **FR-0007**: チェックの実行には、1日あたりの回数の上限を設ける。
  - **FR-0007-01**: 未ログインのユーザーは、IPアドレス単位で数える。
  - **FR-0007-02**: ログイン済みのユーザーは、アカウント単位で数える。
  - 上限の値は後工程で決める。
```

子番号は、入れ子の箇条書きのうち、単独で満たしたかどうかを判定できる子項目にだけ付け、補足説明(上の例の最後の行)には付けない。1階層だけとし、孫項目には付けない。

**接頭辞の決め方**

接頭辞はあらかじめ決めず、項目の種類に合うものが無ければ新しく作る(例: `BR` 事業要件、`FR` 機能要件、`NR` 非機能要件)。

- 略として意味が壊れない範囲で最も短くする。
- 2つの文書をまたいで重複させない(基本設計から要件を「FR-0003 を満たすため」のように指すため)。作る前に両方の文書の「接頭辞」節を確かめる。
- 各文書の「接頭辞」節に、その文書で使う接頭辞と意味を、用語定義と同じ箇条書きで書く。
- 作ったラウンドの出力で、接頭辞と意味をユーザーに伝える。事前の承認は要らない。

```markdown
- **FR**: 機能要件(Functional Requirement)
```

**番号の付け方**

- 番号は接頭辞ごとに `0001` から、子番号は親の項目ごとに `01` から付ける。
- 追加する項目には、文書内の位置によらず、その接頭辞の最大の番号の次を付ける。
- 番号は振り直さず、削除した項目の番号は欠番として再利用しない(解決して消えた未決事項も同じ)。過去の質問や文書の外に残った識別子が、別の項目を指してしまうからである。並び順と番号順は一致しなくてよい。

**既存の文書**

既存の文書の識別子の付け方は、ユーザーが同意するまで変えない。既にある識別子は他から指されている可能性があり、変えると参照が壊れる。

- 識別子が付いている文書: 指示が無ければ、その文書の接頭辞、桁数、区切り方、書き方にならって続きを付ける。ここの規則と違っていても直さず、移行も持ちかけない。もう一方の文書を新しく作る場合も同じ規則に合わせる。「接頭辞」節は、既にある場合にだけ書き足す(無いのに足すと、既存の接頭辞の意味を推定で書くことになる)。
- 識別子が1つも無い文書: 最初のラウンドで導入するかを質問し、同意されるまでは書き足す項目にも付けない(付いた項目と無い項目が混ざるのを避ける)。同意されたら既存の項目すべてに付ける。断られたら以後も付けず、「接頭辞」節も作らない。

### 簡潔に保つ

文書を加筆修正したら、そのたびに書いた内容を読み返して自己確認する。書いた箇所を文書全体と照らし、冗長な言い回し、似た説明の繰り返し、実装に要らない記述があれば直すか削る。文書は後工程で何度も読まれるので、文字数がそのままコンテキストとトークンの消費になる。

- 基準は「直したり削ったりしたら、後工程で間違うか」である。間違うおそれがあれば変えない。
- 内容は変えない。どんなに些細でも仕様が変わる修正は、質問として出して合意を得てから行う。内容を変えない修正は、識別子の付いた項目の削除や統合も含めて確認なしで行う。
- 項目を統合したら一方の識別子を残し、他方は欠番にする。項目の文面を変えたら、他の文書や `TASK.md` に写した文面と、消えた識別子への参照も合わせて直す。
- 対象は `REQUIREMENTS.md`、`SPECIFICATION.md`、`TASK.md`、`docs/design/` 以下の文書、`DESIGN.md` とする。内容を変更しないと定めたもの(基本設計で提示された `DESIGN.md`)と、`CONTEXT.md` とADRは対象外とする。

## 画面設計

- ユーザーから指示が無ければ、SVGで1画面1ファイルを作る。
- 画面設計は要素同士の位置関係を明確にするものだが、この資料を読んだ人が実際の画面を想像できる内容でなければならない。細かな位置を定義しないだけであって、おおよその画面構成の枠組みはここで決める。
  - 画面をどの領域(ヘッダー、ナビゲーション、主となる表示領域など)に分け、それらをどう並べるか、各領域に主要な要素(入力欄、ボタン、一覧とその代表的な項目など)として何を置くかを描く。領域の大きさの比率も、おおよそ実際の画面に近づける。
  - 枠線とラベルで表し、ラベルには実際の画面に出る名称を書く。枠が並んでいるだけで何の画面か分からない図は、位置関係が正しくても役に立たない。
  - 色、フォント、余白の値、厳密な座標はSVGでは定義しない。読み手がそれらを仕様と受け取らないよう、その旨を `SPECIFICATION.md` の「画面設計」節に明記する。
- 画面の要素はコンポーネント化して実装する想定なので、ラベル、フレーム、フォームなどあらゆる要素の構成と描き方を、既に描いた画面に揃える。ばらつくと、同じ部品が画面ごとに別物として実装されてしまう。ランディングページのように特定の画面だけ別の構成にするなど、ユーザーから特別な指示があった場合は例外とする。
- SVGの全面を覆う白い矩形を最初の要素として置き、背景を白にする。描画しない場所は閲覧環境によって透明になり、OSのライトモードとダークモードの設定によっては見づらくなる。
- 別の画面を表示する要素(ボタン、リンク、一覧の項目など)は、`<a href="<遷移先のSVGの相対パス>">` で囲む(`xlink:href` ではなくSVG 2の `href` を使う)。ユーザーがブラウザでSVGを直接開いて画面をたどれるようにし、遷移先のファイルが無いことから画面設計の漏れを見つけられるようにするためである。
  - SVGを作成または変更したら、各 `href` の遷移先のファイルがあるかと、リンクが画面遷移の図の遷移と一致するかを確かめる。遷移先が無い、または食い違う場合は、独断で画面を描き足したりリンクを直したりせず、質問として出す。
- SVGに描く画面構成も、文書と同じく合意が取れた内容だけにする。領域の分け方、並べ方、各領域に置く主要な要素を質問で固め、その回答が出そろった時点でSVGを作る。描く途中で合意に無い点を決める必要が出たら、独断で描かずに質問として出す。
- ユーザーから指示が無ければ、SVGで定義する内容以外のデザインやUXは、画面設計では定義しない。指示があった場合も、SVGには盛り込まない。見た目のデザインは `DESIGN.md` に定義し(「デザイン」)、UXは `SPECIFICATION.md` の「画面設計」節、または `docs/design/` 以下の文書に記録する。ユーザーが既にUXの資料を持っていれば、そのパスを `SPECIFICATION.md` から参照する。厳密な座標は実装で決める事柄なので、基本設計では定義しない。
- mermaid記法で書いた画面遷移の図と `DESIGN.md` を除き、資料は `docs/design/` 以下に置く。その中の置き場所(モノリポジトリでのサブディレクトリ分けなど)と、UXの文書の形式は、内容に合わせて決めてよい。
- 画面遷移の図を作る。ユーザーから指示が無ければ、mermaid記法(`flowchart` または `stateDiagram-v2`)で書く。
  - mermaid記法の図は別のファイルに分けず、`SPECIFICATION.md` の「画面設計」節に `mermaid` のコードブロックとして直接書く。GitHubやエディタのプレビューで図として表示されるので、読み手は別のファイルを開かずに遷移を確かめられる。
  - mermaid記法以外の形式を指示された場合は、図を `docs/design/` 以下に置き、`SPECIFICATION.md` の「画面設計」節から参照する。
  - 画面と、画面同士の遷移(遷移の契機を含む)は、文書と同じく合意が取れた内容だけにする。質問で固め、合意に無い遷移を補わない。

### デザイン

色、タイポグラフィ、角丸、余白、コンポーネントの見た目といったデザインは、`DESIGN.md` で定義する。デザインは実装の工程でユーザーと合意を取ってから定めるので、基本設計ではデザインについての質問を出さず、次の場合を除いて `DESIGN.md` を作らない。

- **提示された場合**: ユーザーが `DESIGN.md` を指し示した場合と、開始時にリポジトリで `DESIGN.md` が見つかった場合がこれに当たる。内容は変更しない。
- **ユーザーが見た目を指示した場合**: `DESIGN.md` が無ければ、その時点で作る。書くのは指示された内容だけにし、`DESIGN.md` として体裁を整えるための質問を足したり、指示に無い値を補ったりしない。残りは実装の工程で合意を取って加筆する。
- 提示された `DESIGN.md` と食い違う見た目の指示があった場合は、`DESIGN.md` を変更するかを質問する。

## `DESIGN.md`

Google Labs の `DESIGN.md` の形式(https://github.com/google-labs-code/design.md)で書く。

- `REQUIREMENTS.md` と同じ場所に置く。
- 書く内容は、文書と同じく合意が取れたものだけにする。
- 形式は今後変わりうるので、書く前に `npx @google/design.md spec` で最新の仕様を出力して読み、それに従う。
- 書いた後に `npx @google/design.md lint <DESIGN.md のパス>` で検証する。合意した内容を変えずに直せる指摘(書式の誤りなど)は直す。エラーや警告のうち、合意した値を変えるか、合意に無い値を足さないと直せないものは、独断で直さずに質問として出す。デザインの質問を出さないと定めた工程でも、この質問は出してよい。
- コマンドが使えない環境(Node.js が無い、ネットワークに接続できないなど)では、その事実を伝え、使えるようにするか、検証せずに進めるかを聞く。

## 実装

### 進め方

1. 文書から実装内容をタスクに分け、`TASK.md` に書く(「`TASK.md`」)。既にあれば、文書と照らして足りないタスクを加え、番号を振り直す。
2. `TASK.md` のパスと一覧を示し、実装するタスクを聞く。ユーザーが既にタスクを指示していれば聞かない。この質問は保留や不問にできない。
3. 選ばれたタスクの実装に必要な質問を、一通り出す。
4. 実装する。途中で質問が必要になったら、その時点で出し、回答を得てから続ける。
5. 選ばれたタスクごとに完了を判定し(「完了」)、完了したタスクを `TASK.md` から消す。番号は振り直さない。並列に実装している他のセッションのタスク番号が途中で変わらないようにするためである。

同じセッションで複数のタスクを選ばれたら、番号順に1つずつ実装する。並列の実装は、ユーザーがセッションを分けて行う。

### 質問すること

詳細設計の文書は作らない。AIはコードから詳細設計に当たる情報をすぐに得られるので、文書にしてもコードとの二重定義になるからである。ただし詳細設計の粒度の事柄も、合意が無ければ質問する。

- 詳細設計の粒度の回答は、コードに反映するだけにする。実装時のすり合わせであって要求ではないので、`REQUIREMENTS.md` の「制約」にも記録しない。
- `REQUIREMENTS.md` や `SPECIFICATION.md` の粒度の不足や矛盾も質問する。実装に必要なのに合意が無い事柄と、文書同士や文書と既存のコードの食い違いがこれに当たる。合意が取れたら、その事柄が属する文書に書き足してから実装する(「前工程との矛盾」)。
- 画面のデザインは「画面の実装」の手順で質問する。
- 保留された質問は、その事柄の粒度に応じて記録する。要件の粒度なら `REQUIREMENTS.md`、設計の粒度やデザインなら `SPECIFICATION.md` の「未決事項」節、詳細設計の粒度なら `TASK.md` の該当するタスクに、保留した理由の要約を書く。保留された事柄に依存する部分は実装しない。

### `TASK.md`

`REQUIREMENTS.md` と同じ場所に置く。

- 1つのタスクは、GitHub の Issue に書き起こす程度の粒度にする。
- 各タスクには、内容と、根拠にした文書の項目の識別子と文面を、「識別子の内容」の形で書く。
- 保留された事柄に依存して実装できない部分を含むタスクには、依存する未決事項も同じ形で添え、解消するまで実装できないことを示す。

```markdown
- **1.** フレームワークのセットアップ
  - <内容>
  - 根拠:
    - `<識別子>`: <項目の文面>
- **2.** データベーススキーマの定義
  - <内容>
  - 根拠:
    - `<識別子>`: <項目の文面>
    - `<識別子>`: <項目の文面>
- **3.1.** APIの実装
  - <内容>
  - 根拠:
    - `<識別子>`: <項目の文面>
  - 未決事項(解消するまで実装できない):
    - `<識別子>`: <項目の文面>
- **3.2.** 画面の実装
  - <内容>
  - 根拠:
    - `<識別子>`: <項目の文面>
```

**タスク番号の付け方**

- 番号は `1.` から連番で付ける。プロジェクト全体への影響が大きいタスクほど前に置く。
- 別のセッションで並列に実装できるタスクは、`3.1.` `3.2.` のように `n1.n2.` の形で付ける。`n1` が同じ子タスクは並列に実装できるものだけにする。
- 同じファイルを変更する可能性があるタスク同士と、一方の結果に他方が依存するタスク同士(例: `DESIGN.md` を作るタスクと、それに従う画面のタスク)は、並列にしない。並列に実装した変更が食い違ったり衝突したりするからである。

### 画面の実装

画面は、次の順で実装する。順序を入れ替えない。

1. ユーザーとデザインの合意を取る。
2. 合意した内容で `DESIGN.md` を作る(既にあれば加筆修正する)。
3. `DESIGN.md` に従って画面を実装する。

デザインを修正するときも同じ順で行い、コードを先に直さない。`DESIGN.md` を実際の画面の見た目と常に一致させ、後から画面を足すときに `DESIGN.md` だけを見て同じ見た目を再現できるようにするためである。

#### 1. デザインの合意を取る

選ばれたタスクの画面に必要な見た目のうち、`DESIGN.md`(あれば)と `SPECIFICATION.md` の「画面設計」節でまだ決まっていないものを、質問と仮画面で固める。色や余白は文章だけでは判断しにくいので、質問で聞くのは見た目の方向を左右する事柄にとどめ、細かな値はユーザーに仮画面の実物を見て確かめてもらう。

1. 質問を出す。仮画面の題材にする画面も、画面設計にある画面の中からどれにするかを質問で決める(画面が1つしか無ければ聞かない)。
2. 回答を元に、確認用の仮画面を1つだけ作る。
   - ブラウザで直接開ける1ファイルのHTMLとし、リポジトリの外の一時ディレクトリに置く。
   - 画面構成は、基本設計のSVGに従う。
   - 不問とされた事柄と、質問していない細かな値は、実装者が値を決めて仮画面に反映する。
3. 仮画面のパスを伝え、この見た目でよいかを質問する(「質問の目的」の例外)。
4. 直したい点が挙がったら、同じ仮画面を直して3に戻る。合意が得られるまで繰り返す。
5. 合意が得られたら、仮画面を削除する。仮画面は成果物ではなく、合意した内容は `DESIGN.md` に残す。

基本設計のSVG(領域の分け方と並べ方、主要な要素)と食い違う要望が出た場合は、前工程との矛盾として扱う。SVGを正としたうえで画面設計を変更するかを質問し、同意されたらSVGを直してから先へ進む。

#### 2. `DESIGN.md` を作る

「`DESIGN.md`」の手順で、合意した内容を書く。実際に実装する内容を書く文書なので、基本設計で作られたものや提示されたものがあれば、実装する内容に合わせて加筆修正する。

不問とされた事柄も、実装者が決めた値を `DESIGN.md` に書く。不問は、ユーザーに特に希望が無いという意味であって、`DESIGN.md` に書かなくてよいという意味ではない。どの値が不問により任意に決めたものかが分かるよう、本文の該当する節にその旨を書く。

#### 3. `DESIGN.md` に従って実装する

画面のコードに現れる見た目は、すべて `DESIGN.md` に書かれたものにする。実装の途中で `DESIGN.md` に無い見た目が必要になったら、コードに直接書かずに1へ戻る。

### 完了

タスクの実装と動作確認(テストの実行など)が終わった時点で、そのタスクを完了とする。保留された事柄に依存する部分が残っているタスクは完了とせず、`TASK.md` に残す。

選ばれたタスクをすべて終えたら、実装した内容、未実装の部分(保留された事柄に依存する部分を含む)、未決事項の数(優先度ごと)を伝える。
