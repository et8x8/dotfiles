# 複数ソース調査

Web、複数文書、データベースなどから情報を集める場合に使用する。所在が明確な1文書を読むだけの作業や、現在のコンテキストで回答できる単純な質問には使用しない。

## 目的

情報源の発見と根拠収集をメインセッション外で行い、必要な結果だけを追跡可能な情報源とともに簡潔に返す。重要な不確実性は残す。

## 調査依頼の作成

開始前に、次を含む自己完結した調査プロンプトを作る。

- 調査対象、探し方、必要な情報と利用目的
- 結果に必要な具体的な事実、比較、日付、項目、根拠
- 解釈に必要な背景、前提、用語、バージョン、環境、期間
- 対象情報源があればその範囲と、Web・ローカル文書・データベースのどれを検索するか
- 明示的な変更依頼がない限り調査だけを行うこと
- 確認済みの事実だけを報告し、捏造、推測による補完、独自の解釈、感想を含めないこと
- 情報が見つからない、または分からない場合も明記すること
- 生文書や未整理の検索履歴ではなく、簡潔に統合した結果を返すこと
- 重要な主張にURL、文書名、データベース名・テーブル名など追跡可能な情報源を付けること

## 委譲調査担当の識別

調査プロンプトの冒頭に次をそのまま含める。

```text
[multi-source-research delegated worker]

このセッションは、multi-source-research skillによって作成された最終調査担当です。
このskillの調査・報告ルールに従い、自分自身で調査してください。
Codex、サブエージェント、別の調査セッションを起動してはなりません。
```

このマーカーを受け取った担当は、本skillの調査・報告ルールに従って自ら調査し、再委譲してはならない。

## 調査担当の選択

次の順で調査担当を一つ選び、選んだ方法だけを使う。

1. ユーザーが調査用のfork済みセッションまたは担当者を指定している場合は、それを使う。追加の担当を起動しない。
2. 現在のエージェント環境にネイティブなサブエージェント／worker機能がある場合は、それを使う。CodexではCodexのサブエージェント機能を使う。他のエージェントでも同様に、その環境の委譲機能を使う。
3. 1と2が使えない非Codex環境に限り、Codex CLIを別セッションの調査担当として使う。

Codexを含むネイティブな委譲機能を使う場合、委譲マーカー、自己完結した調査プロンプト、対象ワークスペースまたは情報源のパス、必要な出力形式を渡す。根拠の収集・統合を任せ、簡潔なレポートと情報源の参照だけをメインセッションへ戻す。

Codexセッションでは、ネイティブ委譲が使えない場合にCLIへ切り替えてはならない。調査を開始せず、委譲機能が利用できないことをユーザーへ報告する。特に `codex exec` の例をCodexセッション内で実行してはならない。

ネイティブ委譲がない非Codex環境では、Codex CLIを調査担当として使う。

Codex CLIは、現在のエージェント環境に委譲機能がない場合だけ使う。環境の判定に `which codex` などのシェル確認を使わない。現在の会話を実行しているエージェントの機能から判定する。

```sh
codex exec --model gpt-6-luna --config 'model_reasoning_effort="<EFFORT>"' --dangerously-bypass-approvals-and-sandbox -o "<OUTPUT_FILE>" "<RESEARCH_PROMPT>" < /dev/null
```

- `<RESEARCH_PROMPT>` は委譲マーカーから始まる完全な調査依頼に置き換える。
- `< /dev/null` は省略しない。`codex exec` は標準入力が端末でない場合、プロンプト引数があっても標準入力をEOFまで読み続けるため、閉じられていない標準入力を渡すと調査が始まらないまま止まる。
- `<OUTPUT_FILE>` は調査担当の最終報告を書き出すファイルで、調査ごとに新しく作る。エージェント環境がセッション用の一時作業ディレクトリを提供している場合はその中に、ない場合は `mktemp` でOSの一時ディレクトリに作成する。`/tmp` など特定のOSを前提にしたパスを直接書かない。
- 調査には時間がかかるため、シェルツールの実行時間上限で打ち切られないよう、バックグラウンド実行できる場合はバックグラウンドで起動し、完了を待つ。
- 成功した場合は `<OUTPUT_FILE>` の内容だけを結果として読む。失敗した場合は標準出力・標準エラーからエラー内容を取り出して報告する。
- プロンプトや結果に秘密情報を含めず、環境変数値を露出させない。

## 調査の実行境界

調査は本skillが作成した担当（Codexではサブエージェント、それ以外では専用セッション）だけが行う。失敗時はメインセッションで代行せず、失敗とエラー内容を必ず報告する。
実行時間の上限は定めない。担当の応答が止まったと判断した場合の中断と再実行は、調査を依頼したエージェントが調査内容に応じて判断する。再実行しても応答がない、または失敗した場合は、失敗とエラー内容を報告する。

## モデルと推論の負荷

調査担当のモデルには `gpt-6-luna` を指定する。Codexのサブエージェント作成時は、モデルを指定できるよう `fork_turns` を `none` または必要最小限のターン数にする。

調査に足りる最低の負荷を選ぶ。

- `low`: 情報は決まっているが所在が不明（例: 特定アプリの最新セットアップ方法）
- `medium`: 調査領域や情報源の種類が比較的明確（例: 要件に合う主要フレームワークと特徴）
- `high`: 多数の情報源の比較や重要な曖昧さの解消が必要
- `xhigh`: 初期使用禁止。`high` で不十分な場合だけ使用

根拠が不十分なら不足を特定し、追加条件を明示して同じ依頼を再実行する。`EFFORT` は `low` → `medium` → `high` → `xhigh` の順に1段階だけ上げ、`xhigh` へ飛ばさない。

## 結果の報告

収集した根拠で元の要求に回答する。簡潔なレポートに次を含める。

1. 直接的な回答または最も役立つ調査結果を最初に示す
2. 重要な主張ごとに、それを裏付ける情報源の所在（URL、ファイルパス、文書名、データベース名・テーブル名など）を対応付けて示す。報告内容に関係しない情報源の所在は示さない
3. 解釈に影響する前提、矛盾、日付、不確実性を示す
4. 未解決の不足情報と、該当時は別の負荷レベルを使った理由を示す

調査担当が根拠を示していない情報源を確認済みと主張しない。

## 情報源の所在と確認

- 報告を受けた側が結果に不足や疑義を感じた場合は、報告に示された情報源（原本）を直接確認してよい
- 報告を受けた側は、情報源の所在を自分で探し直してはならない。必要な所在は調査担当に報告させる。ただし、報告に示された情報源へ直接アクセスして原本を確認することは問題ない
