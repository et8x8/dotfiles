# ユーザー向けドキュメントの作成

共通認識の無い専門用語が突然出てくると、読者は文書を読み進められなくなる。何も知らない読者が冒頭から順に読めば理解でき、作業手順を含む文書なら冒頭から順に実行すれば作業を最後まで完了できる文書を作る。

概念の説明文など作業手順を含まない文書にも、「手順の実行による確認」以外の規則を適用する。

この skill で作る文書では、広く知られた技術名には説明を付けないなど、この skill の用語の規則と食い違う他の指示があっても、この skill の規則を優先する。

## 対象読者を決める

書き始める前に、次の点を明確にする。依頼や会話から決まらない点は、推測で補わずにユーザーに質問する。これらが決まるまで文書を書き始めてはならない。仮定を置いた暫定版も書かない。

- 誰が読むか
- 読者が既に知っているもの(用語、ツール、言語など)
- 読者の作業環境(OS、インストール済みのツールなど)
- 読み終えたときに読者が何を理解し、何をできるようになっているべきか

読者が知っているものとして扱うのは、ユーザーが指定したものだけとする。広く知られた技術名や略語でも、指定されていなければ読者は知らないものとして扱う。

文書の冒頭には、対象読者、前提とする知識、事前に用意しておくもの、読み終えたときに理解できること・できるようになることを書く。

## 構成

何も知らない読者が読む順序で構成する。各節は、それより前に説明した内容だけで理解できるようにする。

文書が複数に分かれる場合は、用語を初めて使う前に、その用語を説明している文書のパスと節名を示す。示した時点から、その用語は説明無しで使ってよい。参照先に実際に説明があることを確かめる。

## 用語

読者が知っているものとして指定されていない用語や略語は、説明無しで使わない。本文だけでなく、括弧内の補足、コードの説明、表、図、例の中に出てくる用語も対象とする。例えば「(HTTP の GET という種類の要求)」のような補足でも、HTTP を説明せずに使ってはならない。

- **主題の用語**: 文書の主題そのものの用語(例: Docker 入門の「コンテナ」)は、使う前に本文で順を追って説明する。
- **主題と関係ない用語**: 初めて出てきた段落の直後に、1〜3行の短い説明を置く。以降はその用語を説明無しで使ってよい。
  - 説明にコードスニペットや図が必要な場合は、行数に数えずに含めてよい。ただし、その用語の説明に必要な最小限にする。
  - 略語は、正式名称と意味を書く。
  - 説明の中で、新たに説明の要る用語を使わない。

主題と関係ない用語の説明の例:

````markdown
設定は `config.yaml` ファイルに YAML 形式で書きます。

> **YAML**: 設定ファイルによく使われる書式です。1行に1項目を `キー: 値` の形で書き、字下げで入れ子を表します。
>
> ```yaml
> server:
>   port: 8080
> ```
````

## ファイル・ディレクトリ・コマンド

- 作成するファイルが複数ある場合や、ディレクトリを作る場合は、最終的なディレクトリ構成をツリーで示してから、各ファイルの作成に進む。
- 読者が作成・編集するファイルの内容を示すときは、コードブロックの直前に、そのファイルのパスと、新規作成か既存ファイルの編集かを必ず書く。ファイル名が無いと、どのファイルの話か読者に分からない。例: 「`my-app/src/main.py` ファイルを作成し、次の内容を書きます。」
- 既存ファイルを編集する場合は、変更箇所を前後の行と共に示し、どこをどう変えるかを書く。
- コマンドは、実行するディレクトリと、成功したときに表示される出力または確認方法を示す。
- 作成するファイルの内容と実行するコマンドを省略しない。「適宜設定する」のように、読者が自分で判断しなければならない書き方をしない。

## 手順の実行による確認

文書を書き終えたら、一時ディレクトリで文書の手順を冒頭から順に実行する。文書に書いてある操作だけを行い、書いていない操作を自分で補わない。失敗した場合や、書いていない操作が必要だった場合は、文書を直してから最初からやり直す。確認を終えた後に手順(コマンド、ファイルの内容、手順の順序、成功の確認方法)を直した場合も、直した後の文書で最初からやり直す。

課金が発生する操作、外部への公開や送信、破壊的な操作(既存のファイルやデータの削除・上書きなど)、秘密情報が必要な操作は実行しない。それらの手順と、実行できなかった手順は未確認として報告する。

一時ディレクトリの外の環境を変える手順(`brew install` や `npm install -g` によるツールのインストールなど)は、一時ディレクトリ内で完結する方法(devbox など)で代わりに実行できれば、それで確認したものとみなしてよい。代わりに実行できない場合は、ユーザーの承認を得てから実行する。

## 読者としての読み直し

完成前に、対象読者になったつもりで冒頭から読み直し、次を確かめる。

- 括弧内の補足、表、図の中のものも含めて、各用語が、ユーザーが知っているものとして指定したものか、初出より前の本文での説明、初出の段落の直後の短い説明、初出より前の参照先のいずれかがある
- すべてのファイルの内容に、そのファイルのパスが書いてある
- 各手順が、それより前の手順の結果だけで実行できる
- コマンドが使うツールが、冒頭の事前に用意しておくものに書いてあるか、それより前の手順でインストールされる(自分の環境で手順が成功しても、ツールが既にインストール済みなら手順の抜けに気づけない)

## 報告

ユーザーに、対象読者、実行して確認した手順、未確認の手順とその理由を報告する。
