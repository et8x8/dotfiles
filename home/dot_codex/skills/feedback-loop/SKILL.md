# Feedback Loop

過去の対話を根拠に、AI エージェント設定の改善を安全に反復する。調査と提案を先に完了し、ユーザーが具体的な変更案を承認するまで設定を変更しない。

## 絶対条件

- ユーザーの最新の指摘、訂正、追加条件を最優先する。
- 承認前は読み取り専用の調査だけを行う。ファイル編集、生成、削除、移動、設定変更、インストール、コミットを行わない。
- 承認後も、承認された変更場所と内容だけを変更する。
- 調査中または実装中に変更範囲を広げる必要が生じた場合は、理由と追加差分を提示して再承認を得る。
- 既存動作と既定値を維持し、ユーザーが求めた改善に必要な最小差分にする。
- 秘密情報、認証情報、環境変数の値、プロジェクト規約で読み取りを禁じられたファイルを調査しない。

## ワークフロー

### 1. 対象となる対話を確定する

1. Skill 呼び出し直前の完了済みユーザー要求と、それに対するアシスタント応答を主な分析対象にする。
2. Skill 呼び出し文に指摘、期待結果、制約が含まれる場合は、それらを最重要の評価基準にする。
3. 直前の対話だけでは原因や期待を特定できない場合に限り、必要な範囲で前々回以前へ遡る。
4. 必要な履歴を取得できない場合は推測せず、不足しているプロンプト、応答、期待結果をユーザーに確認する。

### 2. 期待との差を分析する

次を区別して整理する。

- ユーザーから受けた指摘を、解釈を加えずに抽出したもの
- ユーザーが求めた結果
- 実際の応答または実行結果
- ユーザーが明示した問題点
- 再発を防ぐためにエージェント設定で制御すべき原因
- 一度限りの実装ミスなど、恒久設定へ追加すべきでない原因

プロンプト内の明示的な指摘は、アシスタント自身の推測より優先する。ユーザーの指摘を要約または言い換える場合も、意味を追加・削除せず、AI が判断した問題とは分けて示す。ただし、指摘をそのまま設定へ転記せず、適用範囲と副作用を確認する。

### 3. 既存設定を先に調査する

プロジェクト規約と利用可能なツールに従い、候補となる既存設定を読み取り専用で確認する。

1. 対象プロジェクトと親ディレクトリの `AGENTS.md`
2. ユーザー領域とプロジェクト領域の Skills
3. SubAgents またはエージェント定義
4. Hooks と、それを登録する設定
5. MCP サーバーおよびツール設定

名前だけで判断せず、既に同じ目的を担う指示や仕組みがないか検索する。既存ファイルを改善できる場合は、新しいファイルの作成より既存ファイルの局所的な修正を優先する。

利用可能な仕組みだけを候補にする。SubAgents、Hooks、MCP が存在しない、または問題の解決に不要な場合は追加しない。

### 4. 変更場所と手段を選ぶ

次の基準で配置を決める。

- 特定リポジトリの構造、コマンド、規約、失敗だけに関係する指示はプロジェクト側へ置く。
- 複数プロジェクトで共通する会話方針や作業原則はユーザー側を候補にする。
- 常時守る短い規則は `AGENTS.md` を候補にする。
- 明示的に呼び出す複数手順の作業は Skill を候補にする。
- 独立したコンテキストや専門的な監査が必要な場合だけ SubAgent を候補にする。
- 決定的なイベント処理やコマンド制御が必要な場合だけ Hook を候補にする。
- 外部サービスや専用ツールへの接続が不可欠な場合だけ MCP を候補にする。

最も狭く、既存構成と整合し、対象の原因を直接防げる場所を選ぶ。複数箇所へ同じ規則を複製しない。

### 5. 方針を再監査する

提案前に、候補となる全変更をもう一度確認する。

- 上位または下位の `AGENTS.md`、既存 Skill、SubAgent、Hook、MCP と矛盾しないか
- 同じ指示を複数ファイルへ重複させていないか
- 同用途の別ファイルや仕組みを新設しようとしていないか
- 問題に対して変更範囲が広すぎないか
- 既定動作や無関係なワークフローを変えないか
- 指摘された失敗を具体的に防ぎ、別の予測可能な失敗を生まないか

問題があれば方針を作り直し、再監査を通過するまで提案しない。

### 6. 具体案を提示して停止する

変更を始める前に、次の形式でユーザーへ提示する。

```markdown
## ユーザーから受けた指摘
- `<ユーザーの指摘から抽出した内容。AI の解釈や原因推定を混ぜない>`

## 分析結果
- 期待との差:
- 原因:

## 改善案

### 変更案 1
- 変更場所: `<user または project の具体的なパス>`
- 変更内容: `<追加・修正・削除する内容>`
- 理由: `<原因との対応>`
- 影響: `<変わること・維持すること>`
- 検証方法: `<確認方法>`

## 変更しないもの
- `<調査したが変更不要と判断した設定と理由>`
```

曖昧な「設定を改善する」ではなく、対象パス、設定種別、追加または修正する規則の要旨を明記する。複数案に重要なトレードオフがある場合だけ選択肢を示し、推奨案を明記する。

提示後は明示的な承認を求めて停止する。Plan Mode を利用できる場合は、この調査と承認待ちを Plan Mode で行う。利用できなくても同じ承認ゲートを守る。

### 7. 承認後に適用する

ユーザーの返答を次のように扱う。

- 明確な承認: 承認された案だけを実装する。
- 一部承認: 承認された項目だけを実装する。
- 修正要求または質問: 提案を更新し、再度承認待ちで停止する。
- 曖昧な返答: 承認とみなさず確認する。

実装時は対象ファイルの最新内容を読み直し、ユーザーや他エージェントによる変更を保持する。適用後は提案した検証を実行し、実際の差分が承認範囲内であることを確認する。

## 完了報告

次だけを簡潔に報告する。

- 変更した場所と内容
- 期待との差をどう防ぐか
- 実行した検証と結果
- 未解決事項または承認範囲外として残した項目
